# 从一个报错开始，最后重做了整条分析链路

今天原本只是想修 Prompt Lens 线上视频分析时出现的一个错误：

```text
Error: stream has been aborted
```

但修下去以后，问题一个接一个暴露出来：OpenRouter 401、KIE 返回空结果、KIE 422、Pro 模型上游维护、试用次数只在后端拦截，以及 Vercel Blob、B2、R2 三套存储遗留并存。

这些看起来是不同的报错，实际上都指向同一个问题：视频分析这条链路经历了多次迭代，但存储、模型、密钥、额度和前端状态没有形成统一规则。

这篇记录一下今天遇到的每个问题、为什么会出现、最后怎么修，以及这次修复暴露出的架构教训。

## 一、`stream has been aborted`：请求体太大，不是模型报错

最开始的视频分析流程是：

```text
浏览器读取视频
  ↓
抽取多张关键帧
  ↓
每张图片转成 Base64
  ↓
全部塞进 /api/analyze 请求体
  ↓
服务端再调用视觉模型
```

这个方案在视频短、抽帧少时可以工作，但 Base64 会让图片体积继续膨胀。几十张图片同时进入一个请求后，请求体很大，上传和服务端处理时间也很长。在 Vercel 这类 Serverless 环境里，请求流可能在业务逻辑完成前就被中断，于是前端只看到：

```text
Error: stream has been aborted
```

它并不是 AI 模型主动返回的错误，而是传输方式本身不稳定。

### 修复方式：浏览器直传 R2，分析接口只收 URL

新的流程改成：

```text
浏览器抽帧并压缩
  ↓
申请 R2 临时上传地址
  ↓
浏览器把帧直接上传到 R2
  ↓
/api/analyze 只接收图片 URL
  ↓
模型从 URL 读取图片
  ↓
分析结束后清理临时帧
```

同时补上了几层限制：

- 一次最多 30 帧；
- 单张图片最大 2 MB；
- 服务端校验对象路径必须属于当前用户；
- 无论分析成功还是失败，都在 `finally` 中清理临时文件；
- 分析路由保留足够的执行时间。

这样改完后，大体积图片不再经过 Next.js 分析接口，接口只负责轻量 JSON 和业务编排，链路稳定性明显提高。

## 二、三套存储同时存在：历史兼容代码变成了维护负担

排查上传逻辑时发现，项目里同时残留了三套存储：

```text
Vercel Blob
Backblaze B2
Cloudflare R2
```

它们分别留下了依赖、环境变量、初始化脚本和分支判断。虽然线上主要使用 R2，但维护代码时仍然很难判断某个上传到底会走哪套实现。

这种“先留着也许以后有用”的兼容代码，会让每次故障排查都多出很多无效分支。

最后做了统一收口：

- 删除 Vercel Blob 依赖和相关调用；
- 删除 B2 配置与初始化脚本；
- 上传、临时帧、文档和测试统一以 R2 为准；
- 增加 R2 单一存储路径的验证。

存储层从三套实现缩成一套后，视频分析和普通上传终于共享同一种资源生命周期。

## 三、OpenRouter 401：密钥失效只是表象，模型路由也不够严格

存储问题修完后，线上又出现：

```text
Error: Request failed with status code 401
```

进一步检查后确认，当时的平台 OpenRouter Key 已经无法通过鉴权，接口返回的含义接近“找不到对应用户”。这部分需要更换平台密钥。

但代码里还有一个更隐蔽的问题：用户在分析页选择了某个供应商后，后端有机会继续查找其他已保存的 Key，并静默切换到另一家供应商。

这会导致两个后果：

1. 前端明明选择 KIE，错误信息却来自 OpenRouter；
2. 用户无法判断一次分析究竟消耗了谁的额度。

修复后，分析请求会严格使用前端所选模型对应的供应商，不再偷偷回退到其他供应商。错误信息也按实际供应商返回，避免再出现“选了 KIE，却提示 OpenRouter Key 校验失败”的错位情况。

设置页也随之收口，只保留目前真正支持用户配置的 KIE Key，不再展示已经退出主链路的供应商。

## 四、平台试用和用户 Key 混用：必须显式标记密钥来源

产品规则其实一直很明确：

```text
普通用户：可以使用 2 次平台免费试用
普通用户：配置自己的 KIE Key 后，消耗自己的额度
管理员：可以不限次数使用平台 Key，也可以使用自己的 Key
```

问题在于，旧代码更多是根据“当前有没有 Key”临时判断，没有把密钥来源建模成明确状态。平台 Key 和用户 Key 在同一条调用链里流动，很容易在重构时混淆。

这次增加了明确的来源字段：

```ts
type ApiKeySource = "platform" | "user";
```

后端根据可信的模型定义和当前用户权限决定：

- `platform`：使用服务端环境变量中的平台 KIE Key，并计入免费试用次数；
- `user`：读取当前用户保存的 KIE Key，不消耗平台试用次数；
- 管理员走平台来源时，不受普通用户的两次限制。

平台 Key 只存在服务端，不允许前端传入或覆盖。这样“模型选择”和“谁付费”才真正成为两件可检查的事情。

## 五、平台试用从 OpenRouter 切到 KIE：分支合并状态也会制造线上错觉

中途产品策略发生了调整：平台的两次免费试用不再走 OpenRouter，统一改成使用平台配置的 KIE Key；用户继续使用时，需要配置自己的 KIE Key。

代码改完并推送后，线上却仍然提示 OpenRouter 错误。原因不是新逻辑失效，而是对应提交还没有进入 `main`，线上部署自然仍然运行旧代码。

这次专门补了新的 PR 才把 KIE 平台试用链路合入主分支。

这件事提醒我，下面三个状态不能混为一谈：

```text
代码已经提交
代码已经推送到功能分支
代码已经合入 main 并完成线上部署
```

以后修线上故障，除了看本地代码，还要确认主分支 commit 和部署版本。否则很容易围绕“为什么修了还没生效”继续排查不存在的问题。

## 六、`KIE Gemini API returned empty result`：200 不等于成功

平台试用切到 KIE 后，又出现：

```text
KIE Gemini API returned empty result
```

一开始的解析器只读取 OpenAI 常见结构：

```ts
choices[0].message.content
```

但 KIE 的返回并不总是这种形态，可能出现：

- 外层还有一层 `data`；
- `message.content` 是分段数组；
- 内容位于 Gemini 原生的 `candidates`；
- HTTP 状态是 200，但响应体里的业务 `code` 已经表示失败；
- 模型因为某种原因结束，没有返回正文。

旧代码没有识别这些情况，最后统一抛出“空结果”，把真正的上游错误吞掉了。

修复后，解析器会依次处理：

```text
OpenAI-compatible choices
data 包裹结构
分段 content 数组
Gemini candidates
业务 code / msg
finish_reason
```

日志也增加了经过脱敏和截断的响应结构摘要。这样既不会输出密钥或完整用户内容，又能看到上游究竟返回了什么。

## 七、KIE 422：真正原因是调用了不受支持的 channel

解析器完善以后，原来模糊的“空结果”终于变成了真实错误：

```text
KIE API error (422): The channel is not supported
```

这次没有继续靠猜，而是用最小请求直接测试 KIE：

```text
旧 Gemini 2.5 Flash channel
  -> HTTP 200
  -> 业务 code 422
  -> The channel is not supported
```

随后测试当前可用的 KIE Flash channel：

```text
/gemini-3-5-flash-openai/v1/chat/completions
model: gemini-3-5-flash-thinking
  -> 调用成功
```

旧实现把模型 ID 直接拼进 URL：

```ts
`/${model}/v1/chat/completions`
```

这隐含假设了“模型名等于 channel 名”，但 KIE 的实际规则并不是这样。模型、请求中的 `model` 参数和 URL channel 是三个不同概念。

最后改成显式映射：

```text
产品模型
  ↓
供应商
  ↓
KIE channel
  ↓
请求 model 参数
```

平台试用和用户自带 KIE Key 的 Flash 模型都迁移到可用的 Gemini 3.5 Flash channel，旧模型 ID 则在兼容层映射到新实现，不再动态拼 URL。

## 八、Gemini Pro 为什么仍然报错

排查 Flash 时也测试了 KIE 的 Gemini 2.5 Pro。

它仍然出现在官方资料里，但真实请求返回的是 HTTP 200 加业务 `code 500`，提示服务端维护。这个结果只能说明当时的 KIE 上游通道不可用，不能直接断言模型已经下线。

因此处理方式不是伪造一个成功回退，而是保留清晰的供应商错误，让用户知道当前是上游服务状态问题。对于生产环境，后续还应该给模型增加健康状态和临时下线开关，避免用户反复选择已知不可用的模型。

## 九、两次免费试用不能只靠前端，也不能只靠后端

旧逻辑其实已经在服务端限制了普通用户的两次平台试用。第三次请求会返回 `402`，所以单纯绕过前端并不能无限使用平台 Key。

但前端没有提前查询剩余额度。用户第三次点击后，浏览器仍然会先抽帧、压缩、上传 R2，直到调用分析接口时才得知额度已用完。

这虽然没有造成计费漏洞，但体验很差，也浪费了上传和临时存储资源。

这次增加了额度查询接口，前端会显示剩余次数，并在额度为 0 时：

- 禁用平台试用模型；
- 禁用对应的分析按钮；
- 已保存 KIE Key 的用户，提示切换到自带 Key 的模型；
- 没有 KIE Key 的用户，直接提供进入设置页的入口；
- 管理员显示为不受普通试用次数限制。

后端的 `402` 校验仍然保留，因为前端限制只能改善体验，真正的权限和额度边界必须由服务端执行。

## 十、最终的视频分析链路

修复后的完整链路是：

```text
用户选择实际分析模型
  ↓
前端查询平台试用额度
  ↓
浏览器抽帧并压缩
  ↓
临时帧直传 R2
  ↓
服务端校验用户和对象归属
  ↓
根据模型解析 provider / channel / apiKeySource
  ↓
服务端校验额度和权限
  ↓
调用显式配置的 KIE channel
  ↓
兼容解析响应并记录安全摘要
  ↓
返回分析结果
  ↓
清理 R2 临时帧并刷新剩余额度
```

为了验证它不是“测试里能过”，还用真实公开图片分别跑了两条链路：

```text
平台 KIE Key 路径：成功返回完整中文分析
用户自带 KIE Key 路径：成功返回完整中文分析
```

真实调用耗时在一分钟以上，也再次说明这类视觉分析必须按长任务设计，不能继续把大文件塞进同一个请求里碰运气。

## 十一、这次暴露出的架构问题

回头看，今天并不是连续遇到了很多倒霉的小问题，而是几个架构缺口同时到了必须偿还的时候。

### 1. 缺少单一事实来源

设置页、分析页和后端分别维护供应商与模型信息，导致页面显示和实际调用不一致。后续应该由一份模型注册表统一定义：

```text
modelId
provider
channel
apiKeySource
是否可试用
是否管理员专用
当前可用状态
```

### 2. 模型路由过度依赖字符串

直接从模型名推断 endpoint，在供应商调整 channel 时非常脆弱。外部服务的 URL、请求模型名和产品展示名必须分开建模。

### 3. 平台密钥和用户密钥没有形成领域边界

只判断“有没有 Key”远远不够。密钥来源会直接影响计费、额度、权限和错误提示，应该是后端模型的一部分。

### 4. Mock 测试代替不了真实上游探测

Mock 可以验证请求有没有发出，却无法发现 channel 已失效、业务错误放在 200 响应里、真实响应结构发生变化。关键供应商需要最小 live smoke test，但默认关闭，按需使用真实测试账户执行。

### 5. 错误信息丢失太多

“空结果”这种二次包装错误看似简洁，却把最有价值的 `422 channel not supported` 吞掉了。第三方调用层应该保留状态码、业务错误码、消息和安全响应摘要。

### 6. 部署状态没有进入故障检查流程

功能分支已经修好，不代表线上已经修好。主分支 SHA、PR 合并状态和部署版本都应该成为线上排查清单的一部分。

### 7. 前后端没有共享额度状态

服务端有正确限制，但前端不知道剩余次数，导致用户做完昂贵的准备工作后才失败。后端负责最终裁决，前端负责尽早反馈，两边缺一不可。

## 十二、总结

今天从 `stream has been aborted` 一路修到 KIE 422，最后处理的并不只是一串错误，而是视频分析系统里五个相互关联的边界：

```text
文件怎么传
模型怎么选
请求发到哪里
使用谁的 Key
谁来承担额度
```

最终的解决方案可以概括成几句话：

- 大文件走 R2，业务接口只传 URL；
- 存储统一为 R2，删除 Vercel Blob 和 B2 遗留；
- 模型、供应商和 KIE channel 使用显式映射；
- 平台 Key 与用户 Key 分开建模和计费；
- 普通用户只有两次平台试用，服务端强制限制；
- 前端提前展示额度，避免做完抽帧和上传后才失败；
- 第三方响应要宽松解析，但错误必须完整暴露；
- 修复完成后还要确认 PR、主分支和线上部署确实一致。

这次维护最深的感受是：线上连续报错时，不能只追着最后一条错误信息修。错误往往只是入口，真正要找的是哪一条系统边界没有被明确建模。

当存储、模型、channel、密钥来源和额度规则都成为显式配置后，这条链路才从“目前能跑”变成“后面还能维护”。
