最近给 `prompt-lens` 的登录页换了一个新的背景效果：前景是一个可以自转、拖拽、缩放的 3D 地球，后面再铺一层淡色展开世界地图作为背景板。

视觉效果基本来自 amCharts 的全球地图 Demo，但实际接入过程中踩到了一个比较典型的前端性能问题：**到底是运行时从 CDN 动态加载第三方库，还是把它作为本地依赖打进构建包？**


## 一、最开始的做法：运行时动态加载 CDN 脚本

第一版为了少改项目依赖，我没有直接安装 amCharts，而是在登录页背景组件里动态插入脚本：

```ts
const AMCHARTS_SCRIPTS = [
  "https://cdn.amcharts.com/lib/5/index.js",
  "https://cdn.amcharts.com/lib/5/map.js",
  "https://cdn.amcharts.com/lib/5/geodata/worldLow.js",
  "https://cdn.amcharts.com/lib/5/themes/Animated.js",
];
```

组件 mount 后，按顺序加载这几个 CDN 脚本。加载完成后，从 `window` 上读取：

```ts
const { am5, am5map, am5geodata_worldLow, am5themes_Animated } = window;
```

然后创建两层图表：

- 后层：展开世界地图
- 前层：正交投影地球

这个方案的优点很明显：

1. 不需要立刻改 `package.json`
2. 不增加 Next 构建产物大小
3. 试效果很快，适合原型阶段

但是很快就暴露了问题。

## 二、第一个问题：CSP 拦截第三方脚本

项目里 middleware 配了比较严格的 Content Security Policy：

```ts
"script-src 'self' 'unsafe-inline' 'unsafe-eval'"
```

这意味着浏览器只允许加载本站脚本。登录页动态插入：

```text
https://cdn.amcharts.com/lib/5/index.js
```

会直接被 CSP 拦截。

当时临时修复是把 `cdn.amcharts.com` 加进白名单：

```ts
"script-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.amcharts.com"
```

这样页面能跑了，但它带来一个新问题：为了一个登录页背景，整个站点的脚本来源策略被放宽了。

这不是不能接受，但不够理想。

## 三、第二个问题：生产环境加载慢

后来实际点进登录页时发现：背景不是马上出现，而是要等一会。

原因很直接：进入 `/login` 后，浏览器才开始请求 4 个第三方 CDN 脚本：

```text
https://cdn.amcharts.com/lib/5/index.js
https://cdn.amcharts.com/lib/5/map.js
https://cdn.amcharts.com/lib/5/geodata/worldLow.js
https://cdn.amcharts.com/lib/5/themes/Animated.js
```

这几个请求有几个不可控因素：

- DNS 解析
- TLS 握手
- 第三方 CDN 响应速度
- 用户网络到 CDN 的链路
- 国内网络访问稳定性
- 脚本串行加载顺序

也就是说，登录页背景能不能快点出现，不完全取决于我们自己的站点，而取决于第三方 CDN。

这类问题在开发环境里有时不明显，但到生产环境就会变成用户感知问题。

## 四、这不是传统算法复杂度问题

这是不是和时间复杂度、空间复杂度有关？

严格说，有一点关系，但不是算法题里的那种关系。

这里的主要问题不是：

```text
O(n)
O(nlogn)
O(n²)
```

而是前端加载性能里的 tradeoff：

| 维度 | CDN 动态加载 | 本地依赖打包 |
|------|--------------|--------------|
| 网络请求 | 运行时请求第三方 CDN | 请求本站 Next 静态资源 |
| 首次稳定性 | 受第三方 CDN 影响 | 由自己部署平台/CDN 控制 |
| JS 包体积 | 项目包更小 | 登录页 chunk 变大 |
| CSP | 需要放开 CDN 域名 | 可以保持 `script-src 'self'` |
| 缓存 | 第三方 CDN 缓存 | Next chunk 缓存 |
| 生产可控性 | 较弱 | 较强 |

所以更准确的说法是：这是一个 **加载速度、稳定性、安全策略、包体积之间的工程权衡**。

## 五、改成第二种做法：本地依赖打包

最后把 amCharts 改成了本地依赖：

```bash
pnpm add @amcharts/amcharts5 @amcharts/amcharts5-geodata
```

组件里不再动态插入 script，而是直接 import：

```ts
import * as am5 from "@amcharts/amcharts5";
import * as am5map from "@amcharts/amcharts5/map";
import am5geodata_worldLow from "@amcharts/amcharts5-geodata/worldLow";
import am5themes_Animated from "@amcharts/amcharts5/themes/Animated";
```

这样登录页背景组件还是客户端组件，但它依赖的 amCharts 代码会进入 Next 的构建产物。

同时，middleware 里的 CSP 可以收紧回去：

```ts
"script-src 'self' 'unsafe-inline' 'unsafe-eval'"
```

不再需要：

```text
https://cdn.amcharts.com
```

## 六、代价：登录页 JS 变大

这不是免费优化。

改成本地依赖后，`npm run build` 的结果里，`/login` 的 First Load JS 大约变成：

```text
/login  187 kB  300 kB First Load JS
```

这说明 amCharts 确实被打进了登录页相关 chunk。

也就是说，第二种方案的代价是：

- 登录页 JS 包体积变大
- 首次下载的本站资源更多
- 构建产物变重

但它换来的是：

- 不再等待第三方 CDN
- 线上加载链路更稳定
- CSP 更干净
- 第二次访问可以直接吃浏览器缓存
- 故障边界更清楚

对这个登录页来说，我认为这个 tradeoff 是值得的。因为用户点进登录页时看到背景延迟出现，会直接影响第一印象。

## 七、实现细节：避免 hydration 问题

amCharts 本质上是浏览器端图表库，会直接操作 DOM/canvas。

所以组件里没有让它参与 SSR，而是等客户端 mount 后再初始化：

```ts
const [mounted, setMounted] = useState(false);

useEffect(() => {
  setMounted(true);
}, []);

if (!mounted) {
  return null;
}
```

这样可以避免服务端 HTML 和客户端 amCharts 接管后的 DOM 不一致，减少 hydration mismatch。

地图初始化也放在 `useEffect` 里：

```ts
useEffect(() => {
  if (!mounted) return;

  const root = am5.Root.new(containerRef.current);
  // 创建 MapChart...
  return () => root.dispose();
}, [mounted]);
```

关键点是：

- 只在浏览器端初始化 amCharts
- unmount 时 dispose root
- 不让 amCharts 生成的 DOM 参与 SSR 对比

## 八、视觉层面的调整

最后登录页背景分成两层。

后层是展开地图：

```ts
projection: am5map.geoEquirectangular(),
rotationX: 180,
zoomLevel: 0.96,
```

这里 `rotationX: 180` 是为了改变世界地图的横向断点，让北美/南美被拼到右侧，非洲/欧洲从左侧区域开始。

前层是地球：

```ts
projection: am5map.geoOrthographic(),
panX: "rotateX",
panY: "rotateY",
wheelY: "zoom",
pinchZoom: true,
```

地球支持：

- 自动自转
- 鼠标拖拽
- 滚轮缩放
- 触控缩放

为了让背景不抢登录表单的视觉，展开地图用了比较淡的颜色和透明度：

```ts
fillOpacity: 0.2
strokeOpacity: 0.26
```

## 九、验证结果

改完后做了几类检查。

TypeScript：

```bash
npx tsc --noEmit
```

通过。

生产构建：

```bash
npm run build
```

通过。

浏览器验证里检查了几件事：

1. 登录页正常渲染
2. 展开地图和地球都生成 canvas
3. 地球 canvas hash 随时间变化，说明自转正常
4. 没有请求 `cdn.amcharts.com`
5. 控制台没有 amCharts 相关报错

最关键的是：现在登录页不再依赖运行时第三方 CDN 请求。

## 十、这次的结论

如果只是做一个临时 Demo，CDN 动态加载很方便：

- 快速验证
- 不改依赖
- 不增加构建体积

但如果要上生产，尤其是登录页、首屏、关键路径上的视觉模块，本地依赖打包通常更稳：

- 加载链路可控
- CSP 更安全
- 缓存策略统一
- 故障更容易定位

这次最终选择本地依赖，不是因为它在所有场景下绝对更快，而是因为它让生产环境更可控。


> CDN 方案省包体积，但把稳定性交给第三方；本地依赖方案增加登录页 chunk，但把加载链路收回自己手里。

这就是这次登录页地图背景优化里最核心的工程取舍。
