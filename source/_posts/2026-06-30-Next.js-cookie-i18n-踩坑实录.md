# Next.js 纯 Cookie 模式 i18n 实战与踩坑实录

今天给 `prompt-lens`（AI 视频提示词分析工具）加了一整套中英双语支持。需求看起来很简单——"右上角切语言，所有内容（包括 AI 输出）跟着变"——但实际做下来踩了 5 个坑，其中两个是 next-intl 框架层面的"设计陷阱"。这篇记一下完整实现思路和坑点。

## 一、需求与选型

需求拆解：

1. 页面所有内容支持中英展示
2. 右上角自由切换语言
3. AI 分析结果按当前语言生成
4. 已有中文历史记录保持不动，新分析按当前语言

技术选型上最大的决策是 **locale 存哪里**。两条路：

| 方案 | URL 形态 | 对 better-auth 的影响 |
|------|----------|---------------------|
| URL 前缀（`/zh/dashboard`、`/en/dashboard`） | 变 | 需要改 auth 回调路径，risk 高 |
| Cookie（URL 不变） | 不变 | 零影响 |

选了 Cookie。事后证明这个选择对，但 next-intl 对"纯 cookie 模式"的支持并不友好——这是后面坑 1 的根源。

## 二、整体架构

```
浏览器 cookie (NEXT_LOCALE=zh|en)
        │
        ├─→ middleware.ts        (请求入口：检测/写入 cookie)
        │
        ├─→ i18n/request.ts      (服务端：读 cookie 决定加载哪份 messages)
        │
        ├─→ app/layout.tsx       (服务端：getLocale + NextIntlClientProvider 注入)
        │
        └─→ 组件 useTranslations()  (客户端：直接拿当前 locale 的文案)
```

URL 全程不变（`/dashboard` 始终是 `/dashboard`），locale 只存在 cookie 里。对 better-auth、对已有所有 `<Link>`、对 SEO 都零侵入。

## 三、四个关键环节

### 1. middleware.ts — 请求入口检测

```ts
const cookieLocale = request.cookies.get(LOCALE_COOKIE)?.value;
const acceptLang = request.headers.get("accept-language") ?? "";
// cookie 没命中 → 看 Accept-Language（en 优先 zh）
const detectedLocale = isLocale(cookieLocale) ? cookieLocale : prefersEn ? "en" : "zh";
// 不重写 URL（cookie 模式核心）
if (!isLocale(cookieLocale)) {
  response.cookies.set(LOCALE_COOKIE, detectedLocale, {
    path: "/", maxAge: 60 * 60 * 24 * 365, sameSite: "lax",
  });
}
```

注意：**不重写 URL** 是 cookie 模式的核心。一旦你在 middleware 里 rewrite URL，就回到了路由前缀模式。

### 2. i18n/request.ts — 服务端取 messages

```ts
export default getRequestConfig(async () => {
  const cookieStore = await cookies();
  const cookieValue = cookieStore.get(LOCALE_COOKIE)?.value;
  const locale = isLocale(cookieValue) ? cookieValue : defaultLocale;
  return {
    locale,
    messages: (await import(`./messages/${locale}.json`)).default,
  };
});
```

这里**绕开了 `requestLocale` 参数**，直接用 `next/headers` 的 `cookies()` 自己读。原因见坑 2。

### 3. language-switcher.tsx — 客户端切换

```tsx
const locale = useLocale();
const router = useRouter();
const switchTo = (next: Locale) => {
  document.cookie = `NEXT_LOCALE=${next}; path=/; max-age=31536000`;
  router.refresh();   // 触发服务端重新读 cookie → 重新注入 messages
};
```

`router.refresh()` 而不是 `window.location.reload()`——保留组件状态，体验更顺。

### 4. AI 输出语言透传

这是这次需求里最核心也是最容易遗漏的一环：**i18n 只管 UI 文案，AI 返回的是模型生成的自由文本，不在 messages.json 里**。

所以需要把当前 locale 透传给后端，让后端按 locale 选不同的 prompt：

```ts
// Client
const locale = useLocale() as Locale;
fetch("/api/analyze", {
  body: JSON.stringify({ ..., outputLanguage: locale }),
});

// Server
const { outputLanguage } = body;
analyzeFrames({ ..., outputLanguage });  // 内部 PROMPTS[outputLanguage].single
db.insert(analysisHistory).values({ ..., language: outputLanguage });
```

中英两版 prompt 分别在 `lib/ai/prompts/zh.ts` 和 `lib/ai/prompts/en.ts`：

- 中文维度："画面主体/环境场景/镜头语言/光影照明/美术风格/氛围情绪"
- 英文维度："Subject/Environment/Camera/Lighting/Art Style/Mood"

数据库 `analysis_history` 表加了 `language` 列（`text DEFAULT 'zh' NOT NULL`），旧记录自动回填 `'zh'`，符合"旧中文记录保持不动"的要求。

## 四、踩过的 5 个坑

### 坑 1：`localePrefix: 'never'` 导致 404

**现象**：在 `i18n/routing.ts` 配了 `localePrefix: 'never'`，访问 `/dashboard` 直接 404。

**原因**：next-intl v3 在 `'never'` 模式下**要求** `app/[locale]/...` 动态段 + `setRequestLocale`，否则找不到页面。但我们要的是"URL 完全不带 locale 前缀"的纯 cookie 模式，next-intl 官方并不直接支持。

**解法**：完全不用 `createMiddleware`，改用手动 cookie。`i18n/routing.ts` 只保留 `locales` 和 `defaultLocale` 两个字段：

```ts
export const routing = defineRouting({
  locales: ["zh", "en"],
  defaultLocale: "zh",
});
```

`middleware.ts` 自己读 cookie，不依赖 next-intl 的路由中间件。

### 坑 2：`i18n/request.ts` 签名版本不对

**现象**：旧代码用 `getRequestConfig(async ({ locale }) => ...)`，新版 next-intl 警告这个签名要废弃。

**原因**：next-intl 升级后推荐 `({ requestLocale })`，但我们没走 next-intl middleware 路由，`requestLocale` 其实是空的。

**解法**：绕开 `requestLocale`，用 `next/headers` 的 `cookies()` 自己读。既兼容新版又不依赖路由。

### 坑 3：`extractCorePrompt` 正则强依赖中文

**现象**：英文模式下 AI 返回 `Core Prompt: xxx`，但 `extractCorePrompt` 提取不到核心提示词。

**原因**：旧逻辑硬编码中文标签：`/核心提示词[：:]\s*([^\n]+)/`。

**解法**：正则双语兼容：

```ts
/(?:核心提示词|Core Prompt)\s*[：:]\s*([^\n]+)/i
```

### 坑 4：JSON 语法错误（漏逗号）

**现象**：扩展 `zh.json` / `en.json` 时，运行时报 JSON parse error。

**原因**：`videoGenerate` 块和 `videoEdit` 块之间漏了逗号。

**解法**：加回逗号，并写了校验脚本：

```bash
node -e "JSON.parse(require('fs').readFileSync('i18n/messages/zh.json','utf8')); console.log('OK')"
```

### 坑 5：数据库迁移失败 — `type "analyze_mode" already exists`

**现象**：`pnpm db:migrate` 报错，整个迁移回滚。

**原因**：这是个历史遗留问题——之前开发时一直用 `db:push`（直推 schema，不写迁移记录）改库。这次 `db:generate` 生成的 `0003_blushing_thor.sql` 把所有未记录的变更（创建 `video_generation` 表、给 enum 加值、加 `language` 列）全打包成一个迁移文件。`db:migrate` 想从头跑这个文件，但 `analyze_mode` enum 早就在 0000 时建过了 → 撞重复。

**解法**：改用 `pnpm db:push`。它直接比对当前 schema 与数据库实际状态，只算出"缺一个 `language` 列"这个 diff，安全应用。

> **教训**：`db:push` 和 `db:migrate` 不要混用。`push` 适合开发期快速迭代，`migrate` 适合生产。一旦混用，迁移历史和数据库实际状态会脱节，后面 `migrate` 必撞车。如果要正规化，要么全程 `push`，要么在切换到 `migrate` 前，先手动把 `__drizzle_migrations` 表对齐到当前 schema 状态。

## 五、关键设计权衡

| 决策 | 选择 | 理由 |
|------|------|------|
| locale 存储 | Cookie 而非 URL | URL 不变 → better-auth、所有 `<Link>`、SEO 都零影响 |
| 切换触发 | `router.refresh()` 而非整页刷新 | 保留组件状态，体验更顺 |
| 旧历史记录 | 不动，新记录按当前语言 | `language` 列 `DEFAULT 'zh'`，旧行自动回填 |
| 切换器位置 | 首页而非 dashboard | 用户明确要求"一进入的页面就能切" |
| 未登录访问 dashboard | 跳回首页 | `useEffect` 检测 session，未登录 `router.replace("/")` |
| 迁移工具 | `db:push` 而非 `db:migrate` | 历史已脱节，push 做差量同步更安全 |

## 六、一句话总结

**Cookie 存 locale → middleware 检测 → request.ts 读 cookie 取 messages → layout 注入 Provider → 组件 `useTranslations()` 拿文案 → AI 路径单独透传 `outputLanguage` 给后端 prompt 选择。**

最大的坑是 next-intl 的 URL 前缀模式不适合纯 cookie 方案，必须绕开它自己读 cookie；其次是数据库迁移历史不一致，最后用 `db:push` 做差量同步。
