从零搭建一台 AI Agent Windows 11 虚拟机

这次记录的是从一台已经安装 Oracle VirtualBox 的 Windows 电脑开始，搭建一套独立 AI Agent 实验环境的完整过程。

这套环境的目标不是把所有工具都装到日常电脑里，而是单独准备一台 Windows 11 虚拟机，把 Codex App、Claude Code、OpenCode、Playwright CLI、Hermes、AITDK 等工具集中放进去。

原因很简单：Agent 能力越来越强，能读文件、跑命令、打开浏览器、自动点击网页。如果直接放在真实电脑里，它理论上可能接触到私人文件、Token、SSH Key、.env、浏览器登录态，甚至误删或改坏一些不该碰的东西。

所以这次的核心思路是：

先自己看懂问题，再让 Agent 自动化，最后由自己检查和验收结果。

2. 为什么要单独建虚拟机

如果所有 Agent 工具都运行在日常电脑环境里，它们可能碰到很多完全不需要碰的东西。

比如：

  • 私人文件
  • 浏览器 Cookie
  • SSH Key
  • API Token
  • 项目里的 .env
  • 真实工作目录

Agent 不是一定会乱动，但一旦工具权限给得太宽，它就有机会误操作。

所以更合理的做法是：专门准备一台“AI 实验电脑”。虚拟机出问题，影响基本也限制在虚拟机内部。

7. 撤销上一次提交：git reset --mixed HEAD~1

因为上一次提交里包含了大文件，所以用：

HEAD~1 表示上一个提交。--mixed 的效果是：

  • 撤销最后一次提交；
  • 但保留那些改动的内容，把它们放回工作区（不进入暂存区）。

这样就可以重新整理要提交的内容，把大文件剔除后再重新提交。

三种 git reset 模式的区别：

命令 效果
git reset --soft HEAD~1 撤销提交，改动保留在暂存区
git reset --mixed HEAD~1 撤销提交，改动保留在工作区（默认）
git reset --hard HEAD~1 撤销提交并删除改动，慎用！

10. 大文件该放哪？

视频、音频、模型权重这类大文件，应该放到专门的存储服务里，比如：

  • AWS S3

总结

这次推送看到的几个关键点：

  1. git status 红色是未暂存，绿色是已暂存。
  2. git add 是把改动放进暂存区，git restore --staged 可以撤销暂存。
  3. git commit --amend 用于修改最后一次提交说明，但会改写提交历史。
  4. GitHub 单文件限制 100MB，大文件不能直接推仓库。
  5. 用 git rm -r --cached + .gitignore 把大文件移出版本控制。
  6. git reset --mixed HEAD~1 可以撤销提交但保留改动，方便重新整理。
  7. 大文件应该放到对象存储（R2/S3 等），代码仓库只保留链接。
  8. git restore –staged screenshot-alignment.png screenshot-alignment2.png（用于还未被跟踪的文件，直接从暂存区移到工作区就好了）
  9. git rm -r –cached public/video-templates（用于已经被跟踪的文件，直接把它删掉，并且永不跟踪）

用codex做前端太难了

这个月连续做了很多 AI 工具类落地页。

一开始我对落地页的理解还比较传统：有一个好看的 hero，有价值主张，有一些功能介绍，再加几个案例和 FAQ，最后放一个 CTA。这个结构当然没错，但做多了之后会发现，AI 工具类产品的落地页和普通 SaaS 官网不太一样。

普通 SaaS 落地页更像是在说服用户：“这个产品值得你了解”。

AI 工具落地页更应该让用户立刻感觉：“我现在就可以试一下”。

所以这个月最明显的一个感受是：工具页的入口要尽量前置，甚至直接放在落地页第一屏里。

工具应该成为落地页的一部分

以前很容易把落地页和功能页分得很开。

落地页负责介绍：

  • 这个产品是什么
  • 能解决什么问题
  • 有哪些功能
  • 为什么比别人好

功能页负责使用：

  • 上传文件
  • 输入 prompt
  • 选择模型
  • 点击生成
  • 查看结果

但如果用户已经带着明确需求进来，比如想把参考视频变成同款 AI 视频，或者想把图片变成 PPT，那他最想看到的不是长篇介绍，而是一个可以操作的入口。

所以后来我们开始把工具本身放到落地页上。

第一屏不是只放一个按钮，而是直接放：

  • 输入框
  • 上传区域
  • 示例 prompt
  • 生成按钮
  • 模板入口

用户一进来就知道这个页面能干什么，也能马上开始试。

这个变化很重要。因为 AI 工具的价值不是靠描述建立的，而是靠“我点一下看看会发生什么”建立的。

当然，落地页上的工具入口不一定真的要完整执行生成流程。很多情况下，未登录用户点击生成、Try it now、Create，都可以先跳登录页。关键是交互路径要统一：用户从任何地方表达“我要开始”，都应该进入登录，然后再进入功能页继续使用。

这比把 CTA 散落在不同页面、不同逻辑里要清楚很多。

产品落地页的基本组成

做多了之后，AI 工具类落地页大概可以总结成一套比较稳定的结构。

1. H1 + 价值主张

H1 要直接说清楚产品类别或核心结果。

不要太抽象，也不要为了高级感写得很虚。比如：

这种标题就很好，用户不用思考。

价值主张放在副标题里，解释它为什么有用，比如可以保留动作、构图、镜头语言、风格一致性。

2. 可直接使用的工具

这是 AI 工具落地页最重要的部分。

第一屏最好能有真实输入框、上传框、生成按钮，或者至少是一个非常像真实工具的体验入口。

用户不是来看品牌故事的，他是来解决一个任务的

3. 输入/输出示例

AI 产品很需要示例。

因为用户经常不知道该输入什么，也不知道产品输出会长什么样。

所以页面里要有：

  • 示例 prompt
  • 参考图或参考视频
  • 生成结果
  • 模板案例

这些内容会降低用户的理解成本。

4. 真实效果展示

只放静态图不够。

视频类工具就应该展示视频，PPT 类工具就应该展示生成过程或最终页面。真实效果越靠前，用户越容易判断这个工具是不是他想要的。

这里我们也用到了 Remotion skills($ npx skills add remotion-dev/skills) 来做演示动画。相比直接录屏，Remotion 更适合做可控的产品演示：

  • 镜头节奏可控
  • 文案和 UI 状态可控
  • 可以模拟点击、上传、生成、结果显现
  • 后续改文案和画面也更容易

这对 AI 工具很有用，因为很多生成过程很难稳定复现，做成可编排动画会更适合落地页展示。

5. 核心功能与差异点

功能模块不能只是堆 feature。

每个功能点都应该回答一个问题：

比如参考视频生成，不只是“支持 reference video”，而是“能保留镜头运动、动作结构和画面节奏”。

差异点也不要写成空泛的 better、faster、smarter，而是要说具体差异：

  • 支持参考视频和替换图
  • 可以复用模板 prompt
  • 可以从案例直接创作同款
  • 支持不同风格、场景和镜头运动

6. 使用步骤

步骤模块要简单，最好 3 到 4 步。

用户需要知道流程，但不需要被教程淹没。

常见结构是：

  1. Upload reference
  2. Describe the change
  3. Generate video
  4. Download or iterate

步骤区适合配一段视频或截图，但布局要注意对齐。之前我们就反复调整过标题、视频和步骤之间的位置关系。标题应该独立成一行，视频和步骤再在下面对齐，否则页面会显得拥挤。

7. 使用场景

使用场景不是功能重复，而是帮用户把产品放进自己的工作里。

比如：

  • 广告短片
  • 角色动作
  • 电商产品视频
  • 社媒内容
  • 游戏角色展示
  • 分镜预演

用户看到场景之后，才会觉得这个工具和自己有关。

8. 不同用户的解决方案

同一个工具对不同用户的价值不一样。

设计师关心视觉一致性，营销人员关心转化，创作者关心效率，开发者可能关心流程自动化。

所以可以做一组“适合谁”的模块，让不同用户都能找到自己。

9. 用户评价或信任数据

用户反馈、头像、评价、使用数据这些内容可以增强可信度。

但这部分不能太假。宁愿少一点，也不要写得像模板。

如果没有真实数据，至少可以写成具体的使用反馈，比如：

  • 省去了重新写 prompt 的时间
  • 更容易复现某种镜头
  • 模板可以快速启动创作

10. 相关工具和内链

AI 工具网站通常不是单页产品，而是一组工具矩阵。

所以落地页里应该有相关工具入口：

  • image to video
  • text to video
  • reference to video
  • AI video generator
  • prompt generator

这些内链既帮助 SEO，也帮助用户继续探索。

11. FAQ

FAQ 不是为了凑页面长度，而是回答用户最后的顾虑。

比如：

  • 需要上传什么格式？
  • 生成需要多久？
  • 可以商用吗？
  • 没有参考视频可以用吗？
  • 登录后才能使用吗？
  • 模板会不会自动填 prompt？

FAQ 写得好，可以减少用户在点击前的犹豫。

12. 再次行动按钮

页面底部一定要有再次行动按钮。

用户看完整页后，不应该还要滚回顶部。底部 CTA 要和前面的逻辑一致：Try it now、Generate、Create，统一先跳登录，登录后进入功能页。

视觉设计上反复踩过的点

其实真正花时间最多的，其实不是写功能，而是调视觉细节。

落地页这种东西很容易“看起来差不多”，但差一点就会变成模板感很重的页面。

文字尽量直接写在背景上

一个很明显的偏好是：hero 文案不要总是放在大卡片里。

尤其是首屏，如果把标题、副标题、按钮都塞进一个浮起来的大圆角卡片，就会显得很重，也很像后台模板。

更好的方式是让文字直接写在背景上，用留白、字号、颜色和层级来撑住画面。

如果需要背景图或视频，就让它成为第一视觉，而不是把它包进一个预览卡片里。

少用大面积渐变，尤其是紫色霓虹渐变

很多 AI 网站喜欢紫色、蓝色、霓虹、发光、渐变球。

刚开始看会觉得“很 AI”，但看多了就很疲劳，而且很容易廉价。

我们后面更倾向于轻一点的设计：

  • 背景干净
  • 色彩克制
  • 细线条
  • 微弱阴影
  • 少量强调色
  • 按钮可以有颜色，但不要整个页面都在发光

AI Saas产品不一定要靠霓虹感表达科技感。真正高级的感觉往往来自秩序、留白和内容本身。

页面要有呼吸感

落地页很容易堆模块。

一堆 section 接在一起，如果上下间距不统一，就会显得乱。之前也经常遇到某两个模块太近，和其他模块节奏不一致的问题。

后来应该更注意：

  • section 之间的垂直间距要统一
  • 标题和内容之间的距离要稳定
  • 左右布局要对齐
  • 模块内边距不要忽大忽小
  • 桌面和移动端都要检查

“有呼吸感”不是单纯留很多空白，而是让页面节奏稳定。

字体更适合用干净圆润的无衬线

这一类工具站，我们经常偏向 Outfit 这种字体气质。

它比默认系统字体更有品牌感，但又不会太夸张。标题可以大一些，正文保持清楚，按钮文字不要太挤。

字体大小也要根据容器来调。比如标题想放在同一行，如果放不下，可以适当缩小，而不是硬换行导致结构变弱。

输入框适合灰色细线条

工具类输入区不需要做得很厚重。

灰色细边框、浅背景、轻微圆角、明确 placeholder，通常就够了。上传区也是一样，重点是让用户知道可以点、可以拖、可以上传，不要把上传框做成过度装饰的卡片。

案例卡片要能直接创作同款

模板和案例不只是展示内容。

更好的逻辑是：每个模板视频上都有 Create 按钮。用户点击后，把这个模板对应的 prompt、参考视频、方向说明加载到功能页，然后可以直接创作同款。

如果未登录，就先跳登录；登录后再进入功能页。

这样案例就从“看看效果”变成了“启动创作”。

品牌名字和标识也会影响页面气质

做落地页时，品牌名字和 logo 不只是装饰。

一个 AI 工具如果名字太泛，页面就会很难记。名字、标识、标题、按钮文案、案例风格，要尽量形成一个整体。

比如 reference to video 这种工具，核心就是“从参考到生成”。品牌表达不需要复杂，但要让用户一眼知道这是一个视频生成工具，而不是泛泛的 AI 平台。

logo 也一样，不一定要复杂，但要能在导航栏、favicon、按钮、OG 图里稳定出现。

博客页面也是产品的一部分

博客不是另一个独立的内容系统，它本身就是产品的一部分。

很多 AI 工具的搜索流量不是直接从首页来，而是从某个教程、复盘、案例文章进来。

所以博客文章也应该和产品页互相连接：

  • 教程文章引到工具页
  • 工具页引到相关教程
  • 案例文章展示 prompt 和成品
  • FAQ 可以扩展成博客内容
  • 产品更新可以沉淀成复盘

这样网站不是只有几个孤立页面，而是逐渐形成一个内容网络。

总结

做了这么多落地页之后，我觉得 AI 工具类页面最重要的不是“做得炫”，而是“让用户尽快开始”。

好的落地页应该做到：

  • 用户一眼知道这是干什么的
  • 第一屏就能看到工具入口
  • 案例能直接变成创作入口
  • 真实效果比抽象描述更靠前
  • CTA 逻辑统一
  • 页面视觉轻盈，不压迫
  • 模块节奏稳定
  • FAQ 和内链把用户继续往下带

如果用一句话总结，就是：

它当然需要 H1、价值主张、功能介绍、使用步骤、用户评价、FAQ 和 CTA，但这些内容都应该围绕一个目标展开：降低用户从“我有兴趣”到“我开始用”的距离

背景

一开始文生 PPT 和图生 PPT 都已经能接上 KIE API，也能生成 outline、生成 PPT、生成图片和可编辑图层。但实际使用时有一个明显问题：生成过程太像“等结果”，不像 Gamma 那种“有人正在快速帮你搭建页面”。

用户点完生成后，如果只是看到一个静态 loading 或者一张大卡片，会感觉系统卡住了。尤其是 PPT 生成本身耗时比较长，如果每页都串行生成，用户会觉得速度很慢

所以这次的目标不是单纯把 API 接上，而是把生成过程改成真正的流式体验：

  • 点击生成后立刻进入 workspace。
  • 页面先显示全灰骨架。
  • 后端边生成边推事件。
  • 前端完成一页显示一页。

1. 先塞假内容再替换

早期 outline 和 PPT 生成时，为了让页面看起来“有东西”，会先生成一批 placeholder 内容。

比如 outline 里先出现一些假标题、假 bullet：

真正想要的效果应该是：没生成出来之前就不要显示内容，只显示灰色骨架和动效。生成完了再显现真实内容。

  • 未完成页持续闪动。

这样用户能清楚看到：整套 PPT 正在被搭建。

增加多语言 OCR 识别图片转可编辑 PPT 的文字重叠问题复盘

背景

今天主要卡在一个问题上：图片转可编辑 PPT 时，识别出来的文字大量重叠。

一开始看起来像是“多语言识别不够好”，尤其是韩语、德语和欧洲语言样例中，页面上出现了很多错位文字、重复文字和异常大的文字。但继续排查后发现，真正的问题不是识别不到，而是识别结果被重复加入、过度拆分、错误合并，最后全部渲染成了可编辑文本层。

这个问题在简单页面里不明显，但在投行 PPT、Business Model Canvas、密集表格、复杂版面里会被迅速放大。

问题现象

测试过程中主要出现了几类现象：

  • 同一段文字被叠加了两三次。
  • 原图里一行文字被拆成多个不同大小的文本框。
  • 某些识别结果字号异常大，直接盖住页面其他内容。
  • 页面越密集，生成的文本层越多，重叠越严重。
  • 德语样例中，大量灰色占位文字、栏目标题、正文说明混在一起。
  • 韩语样例中出现了不属于原图的异常混杂文字。

结果就是：明明只想把原图上的文字转成可编辑文字，但页面上变成了密密麻麻的一堆可编辑文本框。

最初判断的偏差

一开始我的判断偏向于“识别不够充分”，所以尝试增强 OCR 能力：

  • 加强 KIE/Gemini prompt。
  • 强调多语言原文照抄，不翻译、不猜测。
  • 增加 OCR audit。
  • 尝试让模型补充遗漏文字。

这个方向在“文字漏识别”的场景里是合理的，但在复杂 PPT 场景里反而会带来副作用。

复杂 PPT 的问题不是文字太少，而是文字太多、版面太密、层次太复杂。每多跑一次 OCR 或视觉分析，就会多出一批候选文本。如果合并策略不够严格，这些候选不会变成补漏，而是变成噪音。

所以后面效果一度变差，根本原因是：我把“提高召回率”放在了“控制重复和稳定版面”前面。

为什么会出现重叠

当前系统里，文字可能来自多路结果：

  • KIE/Gemini 主分析结果。
  • KIE/Gemini OCR audit 结果。
  • 腾讯云 OCR 补充结果。
  • 后处理阶段校准后的文本层。

这些来源的目标本来是互相补漏。但在复杂页面里，它们经常识别到同一块区域。

比如一行德语标题：

  • KIE 主结果识别出整行。
  • OCR audit 又识别出整行。
  • 视觉模型还可能把其中几个词单独识别出来。
  • 后处理再把局部框和整体框都保留下来。

最后，这些结果都进入 textLayer，前端和 PPTX 导出就会把它们全部画出来，于是形成文字重叠。

更严重的是，Gemini/KIE 并不是专门的 OCR 排版引擎。它能理解页面结构，但对密集文字的坐标、字号、文本框边界并不总是稳定。它有时会把背景字、模板占位字、图标旁边的小字、栏目标题都当成同等级文字返回。

这说明问题不只是 OCR，而是 OCR 结果进入可编辑图层之前缺少足够强的筛选和优先级。

后面怎么优化

后面的优化方向从“识别更多”改成了“更保守地接收文本层”。

1. 减少默认 OCR 审核次数

之前为了多语言补漏，KIE 可能会跑更多 OCR audit。后来增加了配置：

默认只走标准模式，不再主动跑过多额外识别。只有手动设置成 exhaustive 时，才启用更激进的多轮 OCR。

这个改变的核心思路是：默认情况下，宁可少识别一点，也不能让页面变成满屏叠字。

2. 增加低质量候选过滤

对 OCR audit 合并结果增加了过滤规则：

  • 置信度太低的候选丢弃。
  • 字号明显异常的候选丢弃。
  • 文本很短但占用面积特别大的候选丢弃。
  • 字符脚本混杂异常的候选丢弃。
  • 与已有文本高度重叠且内容冲突的候选丢弃。

这些规则不是为了让 OCR 更聪明，而是为了阻止明显不可靠的文本进入最终可编辑层。

3. 对密集页面启用保守合并

当页面已有文本层数量很多时，说明这张图大概率是投行页、表格页、Canvas 页或者复杂报告页。

这类页面如果继续追加 OCR 候选，很容易越补越乱。所以后面增加了密集页面保护：

  • 如果已有文本层很多，新的 OCR 候选只要和已有文本明显重叠，就不轻易加入。
  • 额外 OCR 结果更多作为补漏，而不是平等合并。

这个策略的目标是减少重复叠加，而不是追求识别数量最大化。

4. 限制异常字号

有些识别结果即使文本内容对了，字号也可能异常大。前端预览和 PPTX 导出如果完全相信模型返回的字号，就会出现一行字盖住半页的情况。

所以后面在两个地方增加了字号保护：

  • 前端预览时，字号不能超过文本框高度的合理比例。
  • PPTX 导出时，也对字号做类似限制。

这不能彻底解决重复识别，但可以防止单个异常文本层破坏整页视觉。

5. 回滚过度修正

调试中也有一些尝试没有留下。

比如过度清理主文本层、过度调整预览模式、试图用更多规则强行修正复杂版面，这些改动在某些样例上看似有效，但换一张图就可能更乱。

所以后面保留了更稳定的部分：

  • 减少默认 OCR 轮次。
  • 强化低质量候选过滤。
  • 密集页面更保守。
  • 限制异常字号。

没有继续堆过多不稳定规则。

最终形成的处理原则

这次复盘后，我对这个问题的判断变清楚了：

图片转可编辑 PPT 里，OCR 不是越多越好。

真正重要的是进入 textLayer 的结果必须干净、稳定、少重复。因为一旦文本进入可编辑层，用户就会直接看到它，PPTX 导出也会保留它。

后续应该按这个优先级处理：

  1. 专业 OCR 结果优先负责文字内容和坐标。
  2. KIE/Gemini 更适合做版面理解，不应该无限补文字。
  3. OCR audit 只能补漏，不能和主结果平等合并。
  4. 重叠区域应该只保留一个最可信文本层。
  5. 复杂密集页面默认走保守模式。
  6. 渲染和导出阶段都要保护字号和边界。

后续还应该继续做的优化

后面如果继续打磨这个问题，最值得做的是可观测性和来源优先级。

1. 给每个文本层标记来源

例如：

  • kie-main
  • kie-audit
  • tencent-ocr
  • manual
  • postprocess

这样调试时可以快速看出，到底是哪一路在制造重复文本。

2. 做 OCR 来源开关

在调试界面里增加开关：

  • 只看 KIE 主结果。
  • 只看 OCR audit。
  • 只看腾讯 OCR。
  • 看最终合并结果。

这样比盲目改 prompt 或改规则更有效。

3. 做 winner-take-one 合并

同一区域如果出现多个候选，不应该全部保留，而应该选一个赢家。

可以综合考虑：

  • 来源优先级。
  • 置信度。
  • 文本长度。
  • 坐标合理性。
  • 字号合理性。
  • 与其他文本层的重叠程度。

4. 增加复杂页面模式

对 Business Model Canvas、投行页、密集表格这类页面，可以默认更保守：

  • 降低 OCR audit 参与度。
  • 提高新增文本层门槛。
  • 优先保留较完整的文本框。
  • 不轻易加入局部重复词。

总结

这次最关键的反思是：不要把“多识别”误当成“识别质量更好”。

用户真正想要的是：原图上有什么文字，就尽量照抄出来，并且变成可编辑文字。除此之外，不要多加、不要猜测、不要翻译、不要重复。

在这个场景里，最终效果的好坏不是由 OCR 返回了多少文字决定的，而是由这些文字能不能稳定地落到正确位置、以正确大小显示、并且不互相覆盖决定的。

所以后续做图片转可编辑 PPT，应该优先保证：

  • 少重复。
  • 不乱叠。
  • 坐标稳定。
  • 字号可控。
  • 来源清楚。
  • 能导出可编辑 PPTX。

只有在这个基础上，再去追求更高识别率。
