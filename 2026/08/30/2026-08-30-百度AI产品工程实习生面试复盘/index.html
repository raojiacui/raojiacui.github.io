学习笔记

百度 AI 产品工程实习生一面、二面复盘

首先一针见血：事情做了很多，但是缺乏深度。

一面：从 AI 产品开发到完整产品闭环

我主要参与过 AI SaaS 产品从 0 到 1 的落地，同时也独立做过自己的 AI 产品。比如，我自己开发过一款 AI 视频提示词分析工具，从最开始的需求判断、产品设计，到后续的开发、上线和迭代，基本都完整参与过。

因为之前做的产品比较偏向全球用户，所以我平时也会持续关注海外市场。我常会在 Reddit、X 等平台上观察海外开发者和创作者在讨论什么，尤其会通过 Reddit 社区和 GitHub 去寻找用户真实的需求和痛点。

除了用户调研，我也会进行竞品分析，了解同类型的优秀产品是如何解决问题的，再判断我们是否能够做出差异化的体验。

当需求相对明确之后，我会使用 Codex、Claude Code 这类 AI Coding 工具，把产品需求拆解成具体的开发任务，先快速跑通核心功能，再进行测试、产品迭代，以及交互和用户体验上的优化。

产品相对完善之后，我会继续做增长相关的工作，比如外链建设和流量获取。对我来说，做产品并不是把功能开发出来就结束了，而是要从用户需求、竞品分析、快速开发，到上线迭代，再到增长获客，尽可能把整个产品链路跑成一个闭环。

我也很喜欢这种快速把想法做出来，再通过真实用户反馈不断验证和迭代的工作方式。所以看到这个岗位之后，我会觉得它和我的工作方式，以及我感兴趣的方向都比较契合。我也很希望能够参与到秒哒海外版这个产品真正落地的过程中。

谢谢。

二面：产品上线之后，用户从哪里来

一面的时候，我更多介绍了自己在 AI 产品从 0 到 1，以及 AI Coding 方面的经历。

其实除了产品开发之外，我也一直比较关注一个问题：产品上线之后，用户从哪里来，以及如何持续获得低成本的流量和用户。

我对增长的理解是，产品做出来只是第一步，后面还需要解决用户如何发现产品的问题。

以 SEO 为例，我认为核心并不是单纯写很多 Blog，而是先找到目标用户在 Google 上真正会搜索什么，再围绕这些关键词制作内容或页面，把有明确需求的用户带到产品里，最后还要继续观察这些流量能不能转化成注册、使用，甚至付费。

我自己也比较感兴趣的一点是，如何利用 AI 把这套增长工作进一步自动化。

比如关键词发现、竞品分析、内容框架生成、外链机会筛选等环节，都存在大量重复性工作。这些工作可以先交给 Agent 或 AI Coding 工具完成，人更多地负责最后的判断、质量控制和策略调整。

我觉得，AI 产品工程不仅需要快速把产品做出来，也需要真正思考海外用户在哪里、如何让他们发现产品，以及如何让增长工作变得更高效。

我也很希望能够参与到这部分工作中。

谢谢。

面试问题复盘

这部分主要是面试官对项目细节的追问。它们让我意识到，面试官并不只想知道“你做过什么”，还会继续追问“为什么这么做，以及你是否真正理解它”。

1. 自动拆镜是依据什么进行的？

我们的自动拆镜并不是让大模型直接“猜”镜头边界，而是优先使用 PySceneDetect 这样的开源场景检测库进行分析。

当时使用的是 AdaptiveDetector。它会分析视频帧之间的内容变化，并结合局部时间范围内的变化趋势，判断某一帧是否相较于周围帧出现了明显变化。因此，它并不是简单地使用一个固定规则判断每一对相邻帧，在快速运动、镜头晃动或人物动作幅度较大的视频中，适应性会更好一些。

同时，我们还保留了 FFmpeg 的 scene 检测作为兜底方案。FFmpeg 会根据相邻视频帧之间的画面差异计算 scene change score。当分数超过设定阈值时，就认为这里可能发生了镜头切换。

我们的兜底阈值设置为 0.32。这个数值不是绝对最优解，也不是随意拍脑袋决定的，而是一个基于测试和经验的折中值。它在漏切和误切之间取得了相对保守的平衡。

为了避免单纯依赖阈值导致结果失控，还增加了边界规整和时长约束：

  • 过短的片段，例如小于 0.6 秒的片段，会进行合并或过滤；
  • 超过 8 秒的长片段，会继续拆分成更适合后续分析的单元；
  • 检测器、阈值和相关参数都可以通过环境变量进行调整。

所以，系统并不是认为某个阈值永远准确，而是通过“场景检测库优先、FFmpeg 兜底、片段时长约束、参数可配置”这几层机制降低风险。

这些视频分析逻辑最终部署在 Fly.io 的 Worker 上，由独立的 FFmpeg Worker 负责处理。

2. 为什么阈值设置为 0.32？

0.32 更准确地说是一个经验阈值，而不是经过大规模标注数据训练出来的绝对最优值。

在实际视频中，阈值设置得太低，容易把人物快速移动、镜头晃动、光线变化误判成镜头切换；阈值设置得太高，又可能漏掉一些比较自然、变化幅度较小的转场。

因此，我们通过不同类型的视频进行测试，在误切和漏切之间寻找一个相对平衡的点，最终选择了 0.32 作为初始配置。

但我现在的理解是，不能把这个数字包装成“通用最优参数”。更合理的做法应该是：

  1. 建立包含不同内容类型的视频测试集；
  2. 对人工标注的镜头边界进行对比；
  3. 分别统计误切、漏切和边界偏移；
  4. 按视频类型设置不同参数；
  5. 通过用户反馈继续调整阈值。

所以，0.32 是当时工程上的经验选择，后续还需要通过更大规模的样本测试进一步验证。

3. Google 和 GitHub 登录是怎么实现的？

登录部分使用的是 Better Auth 提供的 OAuth 社交登录能力。

前端调用类似 /api/auth/sign-in/social 的接口，并传入 Google 或 GitHub 作为登录提供商。之后由认证系统负责跳转到对应平台的授权页面。

用户授权之后，平台会回调到我们的服务端。Better Auth 会处理授权码交换、用户信息获取以及账号关联，并将用户、账号和会话信息写入数据库中的相关表。

登录成功之后，系统会通过 session cookie 维护登录状态。用户之后访问需要登录的接口时，服务端会读取请求中的会话信息，确认当前用户身份，再决定是否允许继续操作。

这里需要区分两种 Cookie：

  • Prompt Lens 自己的 Cookie，只用于识别用户在 Prompt Lens 中的登录状态；
  • Google、GitHub、YouTube、抖音等平台的 Cookie，属于对应平台的登录凭证。

我们自己的 Cookie 不能代替用户在其他平台上的登录状态。

4. 项目中遇到的最大问题是什么？

当时遇到的最大问题，是视频分享链接解析功能。

设想是，用户不需要上传视频文件，只需要粘贴一个视频分享链接，系统就可以直接分析。这样既能降低用户的使用门槛，也能减少平台自身的存储压力。

但真正实现时，问题并不只是“把 URL 传给 FFmpeg”这么简单。

很多平台的分享链接并不是真实的视频文件地址，而是一个需要经过网页解析、接口请求或鉴权才能访问的页面链接。对于部分非公开视频，平台还会要求登录态、签名参数、请求头或者 Cookie。

而线上服务端无法直接拿到用户浏览器里保存的抖音、YouTube 等平台的 Cookie。Prompt Lens 自己的登录 Cookie 只能证明用户登录了我们的产品，并不能证明用户已经登录了其他视频平台。

因此，当服务端直接使用 yt-dlp 或 FFmpeg 解析某些链接时，就可能遇到登录态缺失、403、链接过期、平台反爬以及音视频分离等问题。

对于公开视频，yt-dlp 可以直接解析其中相当一部分；但它并不能保证解析所有平台、所有类型的视频。后续方案是考虑接入第三方媒体解析服务，由第三方服务完成平台适配、鉴权和真实媒体地址解析，再将返回的媒体 URL 交给 FFmpeg 进行视频分析。

不过，这种方案并不是完全没有成本。它还需要考虑：

  • 解析服务的稳定性；
  • 视频链接的有效期；
  • 第三方服务的调用费用；
  • 用户隐私和平台合规；
  • 视频是否需要临时转存到 R2；
  • 音频和视频流是否需要重新合并；
  • 解析失败后的重试和错误提示。

这让我意识到，产品需求看起来只是“支持粘贴一个链接”，但真正落地时，背后涉及平台兼容性、登录态、反爬、媒体传输、存储成本和合规风险等一整套工程问题。

5. 为什么要充值 GPT？

首先，它可以陪伴我进行日常学习。在遇到不懂的知识、技术问题或者学习方向上的困惑时，我可以和它不断交流和追问，通过对话把问题逐渐弄清楚。

其次，我希望继续迭代自己的 Prompt Lens 项目。这个产品还有很多想法和功能可以完善，GPT 可以帮助我进行需求分析、技术调研、方案设计、代码实现和问题复盘。

比如在视频链接解析、自动拆镜、抽帧策略、第三方服务接入等问题上，我会先和 GPT 澄清需求、比较方案，再结合实际代码和测试结果做决定。

所以，对我来说，充值 GPT 不只是购买一个聊天工具，更是为自己的长期学习和项目实践提供支持。我希望一边学习，一边把自己的产品慢慢搭建和迭代起来。

这次面试之后的体会：事情要做精，而不是只做多

这次面试之后，我也更加重视文档驱动开发。

过去我有时会一上手就开始写代码，遇到问题之后再不断修改。但对于稍微复杂一点的功能，如果没有提前明确目标、边界和验收标准，开发过程中很容易反复返工。

现在我更倾向于先进行需求澄清和技术调研，再写一份简短的需求文档或技术方案，明确：

  • 这个功能要解决什么问题；
  • 哪些内容属于本次范围；
  • 哪些内容暂时不做；
  • 计划采用什么技术方案；
  • 可能存在什么风险；
  • 最终如何验证功能是否完成。

文档不一定要写得很长，但一定要能帮助自己和团队形成共识。

AI 可以辅助我们生成文档、拆解任务和补充方案，但最终的需求判断、技术取舍和结果验收，仍然需要开发者自己负责。

更深刻的体会是，事情不要贪多，一定要做得精。自己使用 AI Coding 工具开发项目，虽然不需要看懂每一行代码，但核心功能的代码逻辑一定要看，要让自己心里有底，同时也要防止 AI 过度设计。

要把 AI 当成放大自己能力的工具，而不是把自己的判断全部交出去。真正需要体现的，是自己在这件事情里面做了什么，以及为什么这样做。

真正重要的是：

  • 为什么选择这个方案；
  • 这个参数是怎么确定的；
  • 有没有大量做过测试；
  • 方案的边界在哪里；
  • 出现异常时如何处理；
  • 如果重新做一次，会如何改进。

这些问题会把“我做过”继续追问成“我是否真正理解”。

做产品不能只追求把事情做出来，还要逐渐做到能够解释清楚、验证清楚，并且知道它为什么有效、什么时候会失效。
