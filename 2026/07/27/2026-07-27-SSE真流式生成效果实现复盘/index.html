SSE（Server-Sent Events） 真流式生成效果实现复盘

背景

一开始文生 PPT 和图生 PPT 都已经能接上 KIE API，也能生成 outline、生成 PPT、生成图片和可编辑图层。但实际使用时有一个明显问题：生成过程太像“等结果”，不像 Gamma 那种“有人正在快速帮你搭建页面”。

用户点完生成后，如果只是看到一个静态 loading 或者一张大卡片，会感觉系统卡住了。尤其是 PPT 生成本身耗时比较长，如果每页都串行生成，用户会觉得速度很慢

所以这次的目标不是单纯把 API 接上，而是把生成过程改成真正的流式体验：

  • 点击生成后立刻进入 workspace。
  • 页面先显示全灰骨架。
  • 后端边生成边推事件。
  • 前端完成一页显示一页。
  • 未完成页继续显示动态骨架。
  • 已完成页停止闪动。
  • 多页并发生成，而不是一页一页等。

最初的问题

最开始的实现有几个误区

1. 先塞假内容再替换

早期 outline 和 PPT 生成时，为了让页面看起来“有东西”，会先生成一批 placeholder 内容。

比如 outline 里先出现一些假标题、假 bullet：

PPT 页面里也会先出现可编辑文字和本地图像占位，然后等 KIE 图片生成后再替换。

这个逻辑看起来像是“进度很快”，但体验上其实不对。用户会误以为这些内容已经生成好了，后面突然被替换，反而有一种不稳定感。

真正想要的效果应该是：没生成出来之前就不要显示内容，只显示灰色骨架和动效。生成完了再显现真实内容。

2. 只有一个地方在动

第二个问题是动效范围太小。

如果只有当前页主画布在闪，左侧缩略图、右侧图层面板、其他页面都静止，用户会感觉生成过程不完整。

更合理的状态应该是全局进入生成态：

  • 左侧缩略图显示骨架。
  • 主画布显示骨架。
  • 右侧 inspector 显示骨架。
  • 未完成页持续闪动。
  • 完成页停止闪动。

这样用户能清楚看到：整套 PPT 正在被搭建。

3. 后端仍然是串行生成

最明显的速度问题来自后端。

原来逻辑是：

如果一页需要 20 秒，10 页理论上就可能要几分钟。

但用户预期更接近：

所以后面把文生 PPT 和图生 PPT 的生成都改成了并发池，目前先设置为并发 4。

为什么完成页不能继续闪

一开始全局生成态下，所有缩略图和主画布都会闪。这个体验也不对。

因为一页已经完成了，还继续闪，用户会以为它还没生成好。

后来改成：

  • 未完成页：继续 skeleton 和扫光动效。
  • 已完成页：停止闪动，显示真实内容。
  • 当前页如果已完成，主画布也不再加 canvasBuilding。

缩略图的动效也只给 pending 页：

这样完成和未完成状态就更清楚。

并发数为什么先定为 4

理论上 10 页可以全部同时生成，但这不一定更快。

因为 KIE、Gemini、FAL、OCR 这些外部服务都有可能限流。如果一次同时发 10 个任务，可能出现：

  • 请求失败。
  • 排队更久。
  • 被限流。
  • 总耗时反而更长。
  • 错误率变高。

所以先设置并发 4。

并发 4 的好处是：

  • 明显比串行快。
  • 不会一下子打爆外部接口。
  • 前端仍然能看到多页同时生成。
  • 谁先完成谁先显示，体验上接近真正流式。

感受

流式生成不只是后端用了 SSE。

真正的流式体验需要后端、前端和视觉状态一起配合

后端要做到：

  • 不等全部完成再返回。
  • 先推 deck 结构。
  • 每页完成就推对应事件。
  • 支持并发生成。
  • 错误时也能推 error 事件。

前端要做到：

  • 读取 SSE stream。
  • 逐个解析 data: 事件。
  • 只更新对应 slide。
  • 维护 completed 状态。
  • 未完成页不显示半成品内容。
  • 完成页停止动效。

视觉上要做到：

  • 没内容时只显示灰色骨架。
  • 骨架要有动感。
  • 完成页要稳定。
  • 不要用假内容冒充生成结果。

后续还可以继续优化

现在的并发 4 只是第一步，后面还可以继续优化。

1. 增加并发配置

可以把并发数做成环境变量：

这样本地、测试环境、线上可以用不同配置。

2. 做任务失败兜底

如果某一页生成失败，不应该让整套 PPT 失败。可以让这一页保留骨架或 fallback 图，同时继续生成其他页。

3. 区分结构生成和视觉生成

文生 PPT 可以先生成可编辑文字结构，再生成视觉图。这样用户更早看到文字版 PPT，图片慢慢补。

但这个方向要谨慎，因为用户之前已经明确不希望先看到半成品内容。所以需要根据产品体验决定。

4. 增加更细的进度事件

现在主要是页级别进度。后续可以增加：

  • task created
  • polling
  • image ready
  • OCR running
  • slide composed
  • PPTX ready

这样进度会更细。

5. 观察真实耗时

后续应该记录每页生成时间：

  • 第几页开始时间。
  • 第几页完成时间。
  • KIE 耗时。
  • OCR 耗时。
  • 导出耗时。
  • 是否 fallback。

有了这些数据，才能判断到底是模型慢、网络慢、并发不够，还是某个后处理慢。

总结

这次 SSE 真流式的核心不是“加一个 loading 动画”，而是把生成过程从一次性返回改成事件驱动。

用户看到的是 PPT 一页一页被搭建起来：

  • 先有骨架。
  • 再有完成页。
  • 未完成继续闪动。
  • 已完成稳定显示。
  • 多页并行推进。

这个体验感觉上是PPT疯狂长出血肉或者有人再快速的帮你搭建，比普通等待更接近真实产品，也更适合 PPT 这种多页、耗时、可逐步完成的生成任务。
